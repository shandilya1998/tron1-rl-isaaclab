# Plans Index

This directory holds the prescriptive documents of the simulation repository, the designs and implementation plans that propose changes to the code within it. A plan document states a problem, grounds it in evidence, surveys whatever literature bears on it, and then sets out the concrete edits that realise the remedy, ordinarily at the granularity of a named file and a named symbol. Documents that record established facts rather than proposed changes live in [../context](../context/README.md) instead.

### kscale_integration.md

The implementation brief for the KScale biped, which entered the tree as a copy of the SD_BRS1 configuration taken at an earlier point in its development and has since fallen behind it on every axis the gait work stream advanced. It compares the two robots morphologically, by reward term, by agent configuration and by environment configuration, closing that comparison with a table of every difference and its consequence. It then reports the measurement of the KScale URDF and its collision meshes, which is the material the original port lacked, and specifies the robot agnostic script that performs it. Its proposed changes rest on three findings that the configuration file cannot show, that the root link frame is rotated ninety degrees from the Isaac Lab convention so that the commanded forward velocity is lateral, that the foot link frame carries its vertical on y so that the sole sits 0.043 m below the ankle rather than the 0.19 m a reader assuming the SD_BRS1 convention obtains, and that the launcher has no branch for this robot and fails open, silently training the TRON1 SoleFoot instead. Its most useful negative result is that no reward function in the shared package hard codes a name, a count or a geometry, so the four missing reward terms are restored by configuration alone and no shared code is edited.

Its chapter 5 opens a second phase and is the part a reader arriving after the first training runs should read first. Parity with the SD_BRS1 was the right criterion for the port and it is exhausted, because a ported reward term is silent about every degree of freedom the exemplar mechanism does not possess, and the two robots differ in kind at exactly one place, the hip yaw joint being `type="fixed"` on the SD_BRS1 and revolute over plus and minus ninety degrees on the KScale. The chapter measures the consequence in the run of 2026-08-25, where the off axis hip joints run at 4.2 times the SD_BRS1's per joint excursion and where the excursion correlates with yaw tracking at a partial correlation of 0.927 once linear tracking is controlled for, which is the signature of a policy turning by twisting its legs rather than by placing its feet. It surveys the three families of published treatment, establishes by forward kinematics that a KScale foot's heading is 0.995 times its hip yaw angle and nothing else, and proposes one swing gated and dead banded task space reward with its weight budgeted against the run's own logged term magnitudes. Its principal negative result is that the `feet_yaw_alignment` function already sitting unwired in the shared module must not simply be wired, its Euler yaw extraction being correct for the SD_BRS1 foot frame and wrong by 70 to 110 degrees on the KScale's permuted one, such that at any negative weight it would drive the feet towards the very splay it is meant to remove.

Every other implementation plan of the project so far has concerned the workspace as a whole, since the pipelines they modify span this repository, the vendored `rsl_rl`, and the Isaac Lab installation together. Those plans live at the workspace level in `../../plans/`, indexed with their implementation status by [../../plans/README.md](../../plans/README.md). Several of them prescribe edits to files within this repository, notably the co-optimisation investigation plan, the learned model design, the symmetry augmentation brief, and the two gait documents, so a reader looking for the rationale behind a configuration or a reward term in this repository should begin at that index rather than here. The plan above is the first to fall wholly inside this repository, with the single exception of the clauses it adds to the workspace launcher, which it records rather than splits into a second document.

## What belongs here

A plan belongs in this directory when its every edit falls inside this repository and it requires no coordinated change to the workspace, the vendored libraries, or the container tooling. A plan for a new robot asset and its task registration, a plan to restructure the environment configuration layering, or a plan to add a reward family would all qualify. A plan that touches the training entry point together with the co-optimisation package and the `djinn` command surface would not, and belongs at the workspace level.

Where the distinction is genuinely unclear, prefer the workspace level, since a plan is more useful over-scoped and findable than correctly scoped and overlooked.

## Conventions

A plan names its target as a file path and a symbol, and quotes surrounding code to locate an edit. Those quotations drift as the sources change, so an edit should be located by symbol name and the quoted code treated as corroboration rather than as an address.

Each plan carries a status banner immediately beneath its title, stating whether its proposals are implemented, partially implemented, superseded, or outstanding, and the date that status was last verified against the live sources. The register above must record the same status, so that a reader may triage without opening the document. On completing a plan, update its banner and record the outcome, together with any divergence from the plan, in the corresponding context document, so that the plan remains a statement of intent and the context record remains the statement of fact.

Cross references within this directory use the bare filename. References to this repository's factual record take the form `../context/NAME.md`, to the workspace record `../../context/NAME.md`, and to the workspace plans `../../plans/NAME.md`.

The writing and change conventions governing these documents are those of the workspace, recorded in `../../CLAUDE.md`, which requires above all that backwards compatibility be preserved absolutely and that new behaviour be carried by an optional argument whose default reproduces the old behaviour exactly.
